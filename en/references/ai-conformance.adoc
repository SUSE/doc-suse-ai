[#ai-conformance-dra]
== Dynamic Resource Allocation (DRA) support

link:https://kubernetes.io/docs/concepts/scheduling-eviction/dynamic-resource-allocation/[Dynamic Resource Allocation (DRA)] is an API that enables flexible, fine-grained resource requests beyond simple counts and has been generally available (GA) since {kube} v1.34.

Verify that all `resource.k8s.io/v1` DRA API resources are enabled:

[source,console,subs="+attributes"]
----
{prompt_user}kubectl api-resources --api-group=resource.k8s.io
----

.Expected output
[source,yaml]
----
NAME                     SHORTNAMES   APIVERSION           NAMESPACED   KIND
deviceclasses                         resource.k8s.io/v1   false        DeviceClass
resourceclaims                        resource.k8s.io/v1   true         ResourceClaim
resourceclaimtemplates                resource.k8s.io/v1   true         ResourceClaimTemplate
resourceslices                        resource.k8s.io/v1   false        ResourceSlice
----

[#ai-conformance-driver-runtime]
== Driver runtime management

DRA is the primary API to verify that GPU drivers and container runtime configurations are correctly installed and maintained on nodes with accelerators. While DRA features continue to evolve across the {kube} ecosystem, platforms utilize Node Feature Discovery (NFD) and GPU Feature Discovery (GFD) to fulfill this requirement via node metadata attestation.

[#ai-conformance-driver-runtime-version]
=== Verifying base container runtime version

To confirm the base engine handling the container lifecycle, query the underlying `{containerd}` runtime via the core Node API:

[source,console,subs="+attributes"]
----
{prompt_user}kubectl get nodes -l nvidia.com/gpu.present=true -o jsonpath='{.items[*].status.nodeInfo.containerRuntimeVersion}'
----

.Expected output
----
containerd://2.2.3-k3s1
----

[#ai-conformance-driver-runtime-accelerator]
=== Verifying accelerator drivers and runtime configurations

Query node labels to programmatically verify the driver installation and the container runtime configuration patch applied to `{containerd}`:

[source,console,subs="+attributes"]
----
{prompt_user}kubectl get nodes -l nvidia.com/gpu.present=true -o jsonpath='{.items[*].metadata.labels}'
----

.Expected output
[source,yaml]
----

* `gpu-driver-upgrade-state: "upgrade-done"` confirms the operator is actively maintaining the lifecycle of these components.

[#ai-conformance-gpu-consistency]
== API consistency across vGPUs and GPUs

Maintaining consistency with the API and request mechanisms of physical and fractional GPUs ensures that workloads, scheduling, policies and user expectations remain identical across physical and virtual backends.

[#ai-conformance-hp-networking]
== High-performance networking

This requirement defines mechanisms to expose specialized network resources (such as RDMA, RoCE and {infiniband} NICs) with discoverable characteristics, enabling pods to attach to multiple network interfaces. While DRA (DRANET) represents the next-generation approach, link:https://github.com/k8snetworkplumbingwg/sriov-network-operator[SR-IOV] combined with link:https://github.com/k8snetworkplumbingwg/multus-cni[Multus] provides a production-proven architecture.

For full configuration instructions, refer to link:https://documentation.suse.com/suse-telco/3.6/html/telco/sriov.html#option2-sriov-helm[Configuring SR-IOV with {rke2a}]. The implementation supports two options:

* *SR-IOV Network Device Plug-in:* A ConfigMap-driven DaemonSet exposing discovered interfaces as {kube} resources (such as `rancher.io/intel_sriov_odu`).
* *SR-IOV Network Operator:* Discovers SR-IOV capabilities and uses `SriovNetworkNodePolicy` to allocate virtual functions (VFs) and generate Multus `NetworkAttachmentDefinition` resources.

[#ai-conformance-hp-networking-verify]
Verify discovered SR-IOV interfaces:

[source,console,subs="+attributes"]
----
{prompt_user}kubectl get sriovnetworknodestates -n sriov-network-operator -o yaml
----

.Expected output (excerpt)
[source,yaml]
----
status:
  interfaces:
    - pciAddress: "0000:3b:00.0"
      driver: "mlx5_core"
      vendor: "15b3"
      deviceID: "1017"
      totalvfs: 8
----

After applying network policies, verify the available network attachment definitions:

[source,console,subs="+attributes"]
----
{prompt_user}kubectl get net-attach-def -A
----

Workload pods can request named SR-IOV resources (for example, `rancher.io/intelnicsDpdk: 1`) and attach interfaces using the `k8s.v1.cni.cncf.io/networks` annotation.

When cluster autoscaling is configured, the system scales accelerator-specific node pools automatically based on pending pod resource requests.

[#ai-conformance-hpa]
== Horizontal Pod Autoscaler (HPA)

Workloads in {productname} scale automatically based on custom AI/ML metrics (such as GPU utilization or inference request latency) using the standard {kube} link:https://kubernetes.io/docs/tasks/run-application/horizontal-pod-autoscale/[HorizontalPodAutoscaler (HPA)].

The following example configures an HPA resource targeting an {ollama} deployment based on GPU utilization:

[source,yaml,subs="+attributes"]
----
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: ollama-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: ollama
  minReplicas: 1
  maxReplicas: 3
  metrics:
  - type: Object
    object:
      describedObject:
        apiVersion: v1
        kind: Namespace
        name: ollama-system
      metric:
        name: gpu_utilization
      target:
        type: AverageValue
        averageValue: "70"
----

== Robust CRD and controller operation

This requirement verifies the reliable operation of complex AI operators, custom resources, and admission webhook validations.

Install the {kubeflow} Training Operator:

[source,console,subs="+attributes"]
----
{prompt_user}kubectl apply -k "github.com/kubeflow/training-operator/manifests/overlays/standalone?ref=v1.8.0"
----

Verify CRD registration and validating webhooks:

[source,console,subs="+attributes"]
----
{prompt_user}kubectl get crds | grep kubeflow
{prompt_user}kubectl get validatingwebhookconfigurations
{prompt_user}kubectl get pods -n kubeflow
----

[#ai-conformance-crd-controllers-webhook-test]
Test webhook rejection by applying an invalid `TFJob` manifest (omitting required fields):

[source,yaml]
----
apiVersion: kubeflow.org/v1
kind: TFJob
metadata:
  name: tfjob-invalid-test
spec:
  tfReplicaSpecs:
    Chief:
      replicas: 1
      template:
        spec:
          containers:
            - name: tensorflow
              # Missing image field intentionally
----

Applying the invalid resource triggers rejection:

[source,console,subs="+attributes"]
----
{prompt_user}kubectl apply -f tfjob-invalid-test.yaml
----

.Expected output
----
Error from server (Forbidden): error when creating "tfjob-invalid-test.yaml": admission webhook "validator.tfjob.training-operator.kubeflow.org" denied the request: spec.tfReplicaSpecs[Chief].template.spec.containers[0].image: Required value: must be required
----
