The {suseai} Observability Extension {ai-stackpack-version} connects AI application telemetry with service and infrastructure views in {sobservability}.
You can inspect model usage, inference services, data services and GPU resources in the same environment.
This guide explains how to configure telemetry collection and migrate from Extension 2.x.

Before you start, refer to xref:ai-monitoring-integrations[] for the software, versions and artifacts that each product requires.
These features require telemetry from the corresponding applications or exporters.

[#ai-monitoring-new-features]
== What is new in version 3.0.0?

Native service integration::
The extension uses StackPack schema 2.0 to add AI metrics and relationships to existing {otelemetry} services and service instances.
Their trace context remains available.

Product views and icons::
The menu:SUSE AI[] group organizes applications, agents, models, inference services, data services and GPUs.
Eight product views show metrics for {vllm}, {ollama}, {litellm}, {milvus}, {qdrant}, {opensearch}, {mlflow} and {mcpo}.
Recognized products have distinct icons in the topology.

Dashboards::
The _SUSE AI {mdash} Overview_ and _SUSE AI {mdash} Model serving_ dashboards show AI application and inference activity.
_SUSE AI {mdash} Gateway & spend_ covers gateway activity and reported costs.
_SUSE AI {mdash} GPU fleet_ covers GPU utilization, memory and temperature.
The dashboards include comparisons with measurements from one hour earlier.

Models and agents::
You can inspect named agents, models hosted by inference services and model usage reported by applications separately.
Available {ollama} models remain visible after unloading.
Their details show loaded state, disk size, memory allocation and context length.

GPU workload context::
Physical GPU devices link to their {kube} nodes and the workload pods allocated to them.

Health monitors::
The 33 monitors cover application operations, model availability and latency, agent dependencies and product health.
They include troubleshooting guidance.

For migration requirements and changes to existing customizations, refer to xref:ai-monitoring-integration-upgrade[].

[#what-is-ai-monitoring]
== What is {productname} monitoring?

Monitoring {productname} involves observing and analyzing the behavior, performance and health of its components.
In a complex, distributed system like {productname}, this is achieved by collecting and interpreting telemetry data.
This data is typically categorized into the three pillars of observability: 

Metrics::
Numerical data representing system performance, such as CPU usage, memory consumption or request latency. 

Logs::
Time-stamped text records of events that occurred within the system, useful for debugging and auditing. 

Traces::
A representation of the path of a request as it travels through all the different services in the system.
Traces are essential for understanding performance bottlenecks and errors in the system architecture. 

[#how-observability-works]
== How monitoring works

{productname} uses {otelemetry}, an open-source observability framework, for instrumenting applications.
Instrumentation is the process of adding code to an application to generate telemetry data.
By using {otelemetry}, {productname} ensures a standardized, vendor-neutral approach to data collection. 

The collected data is then sent to {sobservability}, which provides a comprehensive platform for visualizing, analyzing and alerting on the telemetry data.
This allows administrators and developers to gain deep insights into the system, maintain optimal performance, and troubleshoot issues effectively.
