[#ai-monitoring-user-apps]
= Monitoring user-managed applications

Agent, RAG, tool and training telemetry requires instrumentation in the application code.
The Collector cannot infer values that the application does not report.
For an overview, refer to xref:ai-monitoring-integration-coverage[].

To monitor other applications, use {otelemetry} SDKs or another provider compatible with {otelemetry} semantic conventions.
For example, you can use the {openlit} SDK.
For more details, refer to xref:ai-monitoring-instrument-openlit[]. 

{otelemetry} offers several instrumentation techniques for different deployment scenarios and applications.
You can instrument applications either manually, with more detailed control, or automatically for an easier starting point. 

[TIP]
====
One of the most straightforward ways of getting started with {otelemetry} is using the {otelemetry} Operator for {kube}, which is available in the {sappco}. Find more information in this https://docs.apps.rancher.io/reference-guides/opentelemetry-operator/[extensive
      guide] on how to use this operator for instrumenting your applications. 
====

[#ai-monitoring-native-applications]
== Instrumenting applications for the native integration

The native integration accepts standard {otelemetry} traces and metrics.

.Resource attributes
Set the following resource attributes for each application:

* A stable `service.name`.
* A non-empty `service.namespace`.
* A unique `service.instance.id` for each instance.
On {kube}, use the pod UID.

Use distinct logical `service.namespace` values for services with the same name that must remain separate across clusters.
Propagate the trace context across service calls.

.GenAI attributes
For each call to a model provider, create a client span with the following attributes:

* `gen_ai.operation.name`, `gen_ai.provider.name` and `gen_ai.request.model`.
* `server.address` and `server.port` of the provider endpoint.
* `gen_ai.usage.input_tokens` and `gen_ai.usage.output_tokens`, only if the provider reports them.

For agents, set `gen_ai.agent.name`.

.GenAI metrics
The following example defines the standard GenAI client metrics with the {otelemetry} Python SDK:

[source,python]
----
from opentelemetry import metrics

meter = metrics.get_meter("example.ai")
duration = meter.create_histogram("gen_ai.client.operation.duration", unit="s")
tokens = meter.create_histogram("gen_ai.client.token.usage", unit="{token}")
----

Record the duration of the complete provider call, including streaming, failures and cancellations.
Record token usage with `gen_ai.token.type` set to `input` or `output`.
If your framework already initializes an {otelemetry} SDK, reuse it.

RAG document counts, tool outcomes and training metrics require custom measurements in your code.
Automatic HTTP instrumentation does not provide them.

To verify, run a real operation, including a failed one, and check the trace and metrics in {sobservability}.

== Migrating application telemetry from Extension 2.x

Update application instrumentation to provide the attributes and measurements described in xref:ai-monitoring-native-applications[].
You can keep an existing {otelemetry} SDK; the integration does not require {openlit} or the `RequestsTotal` metric.
For {owui} calls to {ollama}, replace the Pipelines filter as described in xref:ai-monitoring-native-owui-migration[].
Verify telemetry delivery as described in xref:ai-monitoring-native-collector-verify[] before retiring the previous configuration.

[#ai-monitoring-troubleshooting]
== Troubleshooting

No metrics received from any components. ::
+
* Verify the {otelemetry} Collector deployment. 
* Check if the exporter is properly set to the {sobservability} collector and with the correct API key and endpoint specified. 



No metrics received from the GPU. ::
+
* Verify that the Collector uses the permissions in `otel-native-values.yaml`, as described in xref:ai-monitoring-native-collector-deploy[].
* Verify that the Collector loads the bundled base configuration, which includes GPU metric collection.
* Check the {nvidia} DCGM Exporter for errors. 



No metrics received from {milvus}. ::

* Verify if {milvus} chart configuration is exposing the metrics endpoint. 
* Verify if the metrics receiver scraper is configured. 
* For usage metrics, confirm that requests were actually made to {milvus}. 



No metrics received from {vllm}. ::

* Verify if the {vllm} chart configuration is exposing the metrics endpoint. 
* Verify if the metrics receiver scraper is properly configured, in particular, the placeholders. 
* If some metrics are present, but not usage-related ones, verify if you actually made requests to {vllm}. 
* The native Collector preserves `vllm:` metric names.
Use the configuration described in xref:ai-monitoring-native-inference-vector[].



GPU nodes are stuck in `NotReady` status. ::

* Verify if there is a driver version mismatch between the host and the version that the GPU operator expects. 
* You may need to reinstall the {kube} stackpack. 



No tracing data received from any components. ::

* Verify the {otelemetry} Collector deployment. 
* Check if the exporter is properly set to the {sobservability} collector, with the right API key and endpoint set. 



No tracing data received from {owui}. ::

* Verify the SDK and Function configuration as described in xref:ai-monitoring-native-owui[].
* Verify if chat requests actually happened. 



Cost charts are empty. ::

Verify that the application or gateway reports cost metrics.
The {owui} Function reports token usage and duration but does not calculate inference costs.
For {litellm} gateway metrics, follow xref:ai-monitoring-native-litellm[].

There is high demand for storage volume. ::

Verify if sampling is being applied in the {otelemetry} Collector.
