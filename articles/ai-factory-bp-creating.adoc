This guide walks you through creating custom blueprints for {productname} using the command line.
Learn how to quickly adapt an existing blueprint and how to build a full multi-component stack from scratch, supporting both CPU ({ollama}) and {nvidia} GPU ({vllm}) inference.

The instructions assume an operational {kube} cluster with {ranchera} and {productname} installed (including {nvidia} GPU support if using {vllm}), and that you maintain your blueprint files in a Git repository.

[#aif-bp-creating-prerequisites]
== What are the prerequisites?

*On your workstation:*

[source,sh,subs="+attributes"]
----
{prompt_user}kubectl version --client     # all cluster operations
----

*On the target cluster:*

Ensure the cluster satisfies the following requirements:

[source,sh,subs="+attributes"]
----
# 1. The SUSE AI Factory operator (owns the Blueprint and AIWorkload CRDs)
{prompt_user}kubectl get crd blueprints.ai-factory.suse.com

# 2. The SUSE Application Collection Helm repository
{prompt_user}kubectl get clusterrepo application-collection

# 3. Pull credentials for the repository (an Opaque secret with RAW user and token keys)
{prompt_user}kubectl -n <NAMESPACE> get secret application-collection -o jsonpath='{.data}' | head -c 200

# 4. A default StorageClass (required if the blueprint needs PVCs and storage class is not set explicitly)
{prompt_user}kubectl get storageclass | grep '(default)'

# 5. cert-manager (required if any component exposes a TLS ingress, such as the Airflow UI)
{prompt_user}kubectl get crd certificates.cert-manager.io
----

*If the workload requires an {nvidia} GPU:*

[source,sh,subs="+attributes"]
----
{prompt_user}kubectl get nodes -o custom-columns=NAME:.metadata.name,GPU:.status.allocatable.nvidia\\.com/gpu
{prompt_user}kubectl get runtimeclass nvidia
----

[NOTE]
====
Simulated GPU tools (such as kwok or fake-gpu-operator) schedule GPU workloads, but real inference requires physical GPUs.
====

[#aif-bp-creating-quickstart]
== Quick start: copying an existing blueprint

The fastest path to creating a blueprint is copying and adapting an existing one:

[source,sh]
----
wget https://github.com/SUSE/aif/blob/59be88cd2944b433720de3fe0c27042961f0f7e7/charts/aif-operator/files/blueprints/simple-chatbot-with-rag-1.0.0.yaml
----

Edit `my-demo-ollama-1-0-0.yaml` to configure your blueprint:

[width="100%",cols="<34%,<33%,<33%",options="header",]
|===
|Parameter |Original value |New value
|CR file name |`simple-chatbot-with-rag-1.0.0.yaml` |`my-demo-ollama-1-0-0.yaml`
|`metadata.name` |`simple-chatbot-with-rag-1-0-0` |`my-demo-ollama-1-0-0` (use hyphens)
|`labels[.../blueprint-name]` |`simple-chatbot-with-rag` |`my-demo-ollama`
|`spec.displayName` |`Simple Chat Bot with RAG` |`My Demo (Ollama, CPU)`
|`spec.description` |Original description text |Your customized description
|===

Register the blueprint on the cluster:

[source,sh,subs="+attributes"]
----
# Run a server-side dry run first to validate schema
{prompt_user}kubectl apply --dry-run=server -f my-demo-ollama-1-0-0.yaml

# Apply the resource to register it
{prompt_user}kubectl apply -f my-demo-ollama-1-0-0.yaml
{prompt_user}kubectl get blueprints.ai-factory.suse.com
----

Deploy the workload from the {productname} web interface:

. In the navigation menu, select *Blueprints*.
. Select *My Demo ({ollama}, CPU)* and click *Create AIWorkload*.
. Choose the target namespace.
. Monitor the pod deployment status:

[source,sh,subs="+attributes"]
----
{prompt_user}kubectl -n <NAMESPACE> get pods -w
----

[#aif-bp-creating-folder]
== Understanding the blueprint directory structure

While only the custom resource definition is mandatory, organizing files in a standardized directory structure ensures consistency across blueprints:

[source,text]
----
blueprints/<ID>/
  <ID>-1-0-0.yaml        # REQUIRED — the Blueprint CR
  README.md              # Documentation and architecture details
  ATTRIBUTION.md         # Attribution details if derived from an upstream open source project
  clusterrepos/*.yaml    # Additional ClusterRepo definitions to apply before the CR
----

If the workload requires additional {kube} objects, store them in the same directory and document their deployment procedure in `README.md`.

Naming conventions:

* *Directory ID*: Matches the value in `metadata.labels[ai-factory.suse.com/blueprint-name]`.
* *CR file name*: Uses the format `<ID>-1-0-0.yaml`. The `metadata.name` field uses hyphens (for example, `my-demo-ollama-1-0-0`), while `spec.version` and the version label use dots (such as `1.0.0`).
* *Hardware variants*: Maintain CPU and GPU variants in separate sibling directories (such as `<NAME>-ollama` and `<NAME>-vllm`), using `displayName` suffixes such as `(Ollama, CPU)` and `(vLLM, GPU)` and cross-linking them in their respective `README.md` files.

[#aif-bp-creating-writing-cr-ollama]
== Creating a Blueprint CR for CPU inference with {ollama}

[#aif-bp-creating-header-metadata]
=== Header and metadata

The metadata section defines the unique identity and labels for the blueprint:

[source,yaml]
----
apiVersion: ai-factory.suse.com/v1alpha1
kind: Blueprint
metadata:
  labels:
    ai-factory.suse.com/blueprint-name: my-demo-ollama
    ai-factory.suse.com/blueprint-version: 1.0.0
  name: my-demo-ollama-1-0-0
----

Add a comment block at the beginning of the file summarizing what the blueprint deploys, which models it serves, and any differences from sibling variants. Because `kubectl apply` preserves comments in the repository source, this provides essential context for future maintenance.

[#aif-bp-creating-spec]
=== Defining the blueprint specification

The `spec` section outlines the display metadata and prerequisites:

[source,yaml]
----
spec:
  source: Custom
  displayName: My Demo (Ollama, CPU)
  version: 1.0.0
  description: |
    Deploys a demonstration stack running local models on CPU using Ollama.

    This blueprint deploys Ollama in-cluster with persistent storage while maintaining a lightweight resource footprint.

    Prerequisites: The SUSE AI Factory operator, the application-collection ClusterRepo and credentials secret, and a default StorageClass. After registering, create an AIWorkload from this blueprint in the web interface.
----

Provide a concise description that ends with a clear summary of prerequisites. This description is displayed directly to users in the {productname} web interface.

[#aif-bp-creating-choosing-chartrepo]
=== Selecting a chart repository

The `chartRepo` parameter must reference an active {rancherprime} `ClusterRepo` resource on the target cluster. Standard repositories in {productname} include:

[width="100%",cols="<34%,<33%,<33%",options="header",]
|===
|Repository (`chartRepo`) |Contents |Pre-registered
|`application-collection` |{sappco} charts (`ollama`, `vllm`, `apache-airflow`, `postgresql`, `grafana`) |Yes, on {productname} clusters.

|`suse-ai-registry` |{suseai} charts (`qdrant`, `litellm`) |Yes, on {productname} clusters.
|===

If a chart is not in a pre-registered repository, add a `ClusterRepo` manifest in `clusterrepos/`. For more information, see xref:aif-bp-creating-extra-helm-repos[].

To identify available versions of a chart in the repository:

[source,sh,subs="+attributes"]
----
{prompt_user}kubectl get clusterrepo application-collection -o yaml | grep -A2 downloadTime
{prompt_user}helm search repo application-collection/ollama --versions | head
----

[#aif-bp-creating-example-values]
=== Configuring chart values

Configure chart values under the `values` key:

[source,yaml]
----
    values:
      # Pin the service name to prevent Helm release name prefixes
      fullnameOverride: ollama
      image:
        pullPolicy: IfNotPresent
        registry: dp.apps.rancher.io
        repository: containers/ollama
        tag: 0.21.2-11.48
      persistentVolume:
        enabled: true
        accessModes:
        - ReadWriteOnce
        size: 20Gi
      service:
        port: 11434
        type: ClusterIP
      env:
      - name: QDRANT_URL
        value: http://qdrant:6333
----

Use `ClusterIP` services and forward local ports with `kubectl port-forward` during testing. Define an `ingress` block only when a component provides a web user interface that requires external access.

[#aif-bp-creating-example-ollama]
=== Adding an {ollama} component

The following configuration defines a standard {ollama} CPU component:

[source,yaml]
----
  - chartName: ollama
    chartRepo: application-collection
    chartVersion: 1.55.0
    values:
      fullnameOverride: ollama
      image:
        pullPolicy: IfNotPresent
        registry: dp.apps.rancher.io
        repository: containers/ollama
        tag: 0.21.2-11.48
      ollama:
        gpu:
          enabled: false
          draEnabled: false
        models:
          pull:
          - qwen2.5:0.5b
          run:
          - qwen2.5:0.5b
        port: 11434
      persistentVolume:
        enabled: true
        accessModes:
        - ReadWriteOnce
        size: 20Gi
      service:
        port: 11434
        type: ClusterIP
----

Key considerations for model management:

* Models listed under `models.pull` are downloaded on initial startup. For demonstrations, lightweight models such as `qwen2.5:0.5b`, `llama3.2:1b`, and `moondream:1.8b` (vision) initialize quickly.
* Models listed under `models.run` remain in memory. When serving multiple models, configure `extraEnv` variables such as `OLLAMA_KEEP_ALIVE` and `OLLAMA_MAX_LOADED_MODELS`.
* Both embeddings and chat endpoints are served by the same service (`http://ollama:11434` in-cluster).

[#aif-bp-creating-considerations]
=== Operational considerations

Keep the following operational best practices in mind when constructing blueprints:

* *Set `fullnameOverride`*: Always define `fullnameOverride` where supported. Without it, {helm} prefixes the service name with the generated release name, which breaks port-forwarding scripts and internal DNS resolution.
* *Pin generated secrets in Airflow*: When using Apache Airflow, pin the generated secret keys so that pod templates remain stable across {fleeta} reconciliation cycles:

[source,yaml]
----
      # Pin generated secret keys to prevent Fleet reconciliation loops
      fernetKey: "Nv3aCd-3agJbJG1QxzKMezX5pJZB4fRpZIrqhdS-MA4="
      jwtSecret: "72873f21d1682ddc023f0815344d1cdc0157e59c9c5480bcb430686d6ed466d3"
      webserverSecretKey: "bb3ea2e3f0a3ad96a2f440ab3ca4e3406985aaf72182662ebd339f53a7a28a7a"
----

[NOTE]
====
For production environments, reference pre-created {kube} secrets rather than hardcoding static secrets in the blueprint definition.
====

* *Disable unused sub-charts*: When using `LocalExecutor` with Airflow, set `redis.enabled: false` and `flower.enabled: false` to avoid deploying unnecessary pods that consume cluster resources.

[#aif-bp-creating-extra-helm-repos]
== Managing additional {helm} repositories

If a component requires a chart repository that is not registered on the cluster by default, create a {rancherprime} `ClusterRepo` resource and store it in `clusterrepos/`. The `metadata.name` value must match the `chartRepo` parameter in the Blueprint CR.

For example, to register an HTTPS repository:

[source,yaml]
----
apiVersion: catalog.cattle.io/v1
kind: ClusterRepo
metadata:
  name: openmetadata
spec:
  url: https://helm.open-metadata.org
----

To register an OCI registry:

[source,yaml]
----
apiVersion: catalog.cattle.io/v1
kind: ClusterRepo
metadata:
  name: bitnami
spec:
  url: oci://registry-1.docker.io/bitnamicharts
----

Apply repository resources before registering the blueprint:

[source,sh,subs="+attributes"]
----
{prompt_user}kubectl apply -f clusterrepos/
{prompt_user}kubectl get clusterrepo <REPO_NAME> -o jsonpath='{.status.conditions}'   # Wait for Downloaded status
{prompt_user}kubectl apply -f my-demo-ollama-1-0-0.yaml
----

Note upstream chart licensing in the file comment header when using non-SUSE charts.

[#aif-bp-creating-vllm-variant]
== Creating a GPU inference variant using {vllm}

Hardware variants are organized in separate directories. Create a GPU variant from your CPU base configuration:

[source,sh]
----
cp -r blueprints/my-demo-ollama blueprints/my-demo-vllm
cd blueprints/my-demo-vllm
mv my-demo-ollama-1-0-0.yaml my-demo-vllm-1-0-0.yaml
----

Update the resource fields following the renaming checklist in xref:aif-bp-creating-quickstart[]:

1. Set `spec.displayName` to `My Demo (vLLM, GPU)`.
2. Update the `spec.description` text to specify {nvidia} GPU requirements.
3. Cross-reference the sibling CPU variant in `README.md`.

[#aif-bp-creating-swap-ollama-vllm]
=== Replacing {ollama} with {vllm}

Replace the `{ollama}` component definition with the `{vllm}` component:

[source,yaml]
----
  - chartName: vllm
    chartRepo: application-collection
    chartVersion: 0.1.10
    values:
      servingEngineSpec:
        runtimeClassName: nvidia
        modelSpec:
          - name: qwen25-vl-3b
            registry: dp.apps.rancher.io
            repository: containers/vllm-openai
            tag: "0.19.0-5.29"
            modelURL: Qwen/Qwen2.5-VL-3B-Instruct
            replicaCount: 1
            requestCPU: 6
            requestMemory: "16Gi"
            requestGPU: 1
            pvcStorage: "50Gi"
            vllmConfig:
              maxModelLen: 32768
              dtype: bfloat16
              gpuMemoryUtilization: 0.9
              # Vision flags: enable remote code execution and limit images per prompt
              extraArgs:
              - "--trust-remote-code"
              - "--limit-mm-per-prompt.image=2"
      routerSpec:
        enableRouter: true
        serviceType: ClusterIP
        containerPort: 8000
        servicePort: 80
----

Key configuration notes:

* *`name` and `modelURL`*: The `name` parameter provides a resource label compliant with {kube} naming standards. The `modelURL` parameter identifies the {huggingface} model repository to serve.
* *GPU allocation*: Each entry under `modelSpec` requests dedicated GPU resources (such as `requestGPU: 1`). Multiple models run behind a unified OpenAI-compatible routing endpoint (`vllm-router-service:80`), allowing clients to select models by name.
* *Memory management*: Tune `maxModelLen` to fit the model within GPU memory before adjusting `gpuMemoryUtilization`.
* *Common arguments*: Use `--trust-remote-code` and `--limit-mm-per-prompt.image=N` for vision models. Use `--enable-auto-tool-choice --tool-call-parser=hermes` for function calling.

[#aif-bp-creating-reaching-vllm]
=== Accessing the {vllm} service

Test the model endpoint by forwarding the service port locally:

[source,sh,subs="+attributes"]
----
{prompt_user}kubectl -n <NAMESPACE> port-forward svc/vllm-router-service 8000:80
{prompt_user}curl -s localhost:8000/v1/models | python3 -m json.tool
----

[NOTE]
====
If the Helm release uses a custom name, the service follows the naming convention `<RELEASE_NAME>-router-service`.
====

Because {vllm} provides an OpenAI-compatible API, point your client applications to `/v1/chat/completions` on the router service port.

[#aif-bp-creating-gated-models]
=== Managing gated models

Certain models require accepting terms of use on {huggingface} before download. To provide credentials securely:

. Configure the `hf_token` key in `modelSpec`.
. Avoid hardcoding secret tokens directly into the Blueprint CR or git repositories.
. Reference pre-created {kube} secrets containing the token in production environments.

[#aif-bp-creating-useful-hybrid]
=== Configuring hybrid architectures

You can combine GPU and CPU inference components in the same blueprint. For example, deploy `{vllm}` with GPU acceleration for large language and vision models, alongside an `{ollama}` CPU instance dedicated to lightweight text embedding models (such as `nomic-embed-text`). This preserves GPU resources while maintaining high-throughput text embeddings.

[#aif-bp-creating-publish-run]
== Publish and run end to end

[source,sh]
----
git add blueprints/my-demo-ollama
git commit -m "Add My Demo (Ollama, CPU) blueprint"
git push
----

Push changes to your Git repository *before* deploying if the blueprint uses Apache Airflow: git-sync pulls DAGs directly from the pushed branch.

Deploy and verify the blueprint components in sequence:

. Apply any required custom {helm} repository resources:
+
[source,sh,subs="+attributes"]
----
{prompt_user}kubectl apply -f blueprints/my-demo-ollama/clusterrepos/
----

. Register the blueprint resource on the cluster:
+
[source,sh,subs="+attributes"]
----
{prompt_user}kubectl apply -f blueprints/my-demo-ollama/my-demo-ollama-1-0-0.yaml
{prompt_user}kubectl get blueprints.ai-factory.suse.com
----

. In the {productname} web interface, navigate to *Blueprints*, select your blueprint, and click *Create AIWorkload*. Choose the target namespace.

. Verify that the pods and PVCs initialize correctly:
+
[source,sh,subs="+attributes"]
----
{prompt_user}kubectl -n <NAMESPACE> get pods -w
{prompt_user}kubectl -n <NAMESPACE> get pvc
----

. If using Apache Airflow, unpause and execute the DAGs:
+
[source,sh,subs="+attributes"]
----
{prompt_user}kubectl -n <NAMESPACE> port-forward svc/apache-airflow-api-server 8080:8080
----

. Forward local ports for any service that needs to communicate with the client or user interface.

To clean up, delete the `AIWorkload` from the {productname} web interface, then delete the blueprint custom resource:

[source,sh,subs="+attributes"]
----
{prompt_user}kubectl delete -f blueprints/my-demo-ollama/my-demo-ollama-1-0-0.yaml
----

[#aif-bp-creating-troubleshooting]
== How to troubleshoot blueprint deployment issues

The following table lists common deployment symptoms and their resolutions:

[width="100%",cols="<40%,<60%",options="header",]
|===
|Symptom |Resolution
|Ollama attempts to pull `{\{MODEL}}`. |Replace template placeholder strings with literal model identifiers in the CR.

|Charts fail to resolve or pods are not created. |Ensure the target `chartRepo` exists as an active `ClusterRepo`. Apply repository manifests in `clusterrepos/` and verify the `Downloaded` condition.

|Airflow pods restart repeatedly without entering the `Ready` state. |Pin generated secret keys (`fernetKey`, `jwtSecret`, `webserverSecretKey`) to prevent Fleet reconciliation loops.

|Port-forward or cluster DNS lookups fail. |Ensure `fullnameOverride` is specified in chart values to prevent release name prefixes in service names.

|DAGs do not appear in the Airflow interface. |Verify git-sync parameters (`repo`, `subPath`, `branch`), confirm the repository is reachable from the cluster, and ensure local commits have been pushed.

|DAGs appear in Airflow but do not run. |Ensure DAGs are unpaused in the Airflow user interface.

|DAG import fails on third-party packages. |Package required dependencies into a customized container image.

|`FileNotFoundError` on `include/` paths. |Store referenced files within `dags/`, as only `dags/` is synchronized by default.

|Pods remain in `Pending` state on GPU nodes. |Verify that the {nvidia} GPU Operator is running, the `nvidia` RuntimeClass exists, and requested GPUs do not exceed allocatable cluster capacity.

|PVC remains in `Pending` state. |Configure a default `StorageClass` or explicitly define an existing storage class in `values`.

|`ImagePullBackOff` from `dp.apps.rancher.io`. |Verify the `application-collection` credentials secret. Ensure the token string contains only the raw token value without environment variable prefixes.

|vLLM pods terminate with out-of-memory errors. |Reduce `maxModelLen`, then adjust `gpuMemoryUtilization`.

|User interface connects but API calls fail. |Verify active `kubectl port-forward` processes and check whether environment variables point to `localhost` rather than internal cluster service addresses.
|===

Common diagnostic commands:

[source,sh,subs="+attributes"]
----
{prompt_user}kubectl -n <NAMESPACE> get pods,svc,pvc
{prompt_user}kubectl -n <NAMESPACE> describe pod <POD_NAME>
{prompt_user}kubectl -n <NAMESPACE> logs deploy/<DEPLOYMENT_NAME> --tail=100
{prompt_user}kubectl get clusterrepo -o wide
----

[#aif-bp-creating-minimal-skeleton]
=== Minimal two-component blueprint template

[source,yaml]
----
apiVersion: ai-factory.suse.com/v1alpha1
kind: Blueprint
metadata:
  labels:
    ai-factory.suse.com/blueprint-name: my-demo-ollama   # == folder name
    ai-factory.suse.com/blueprint-version: 1.0.0         # dots
  name: my-demo-ollama-1-0-0                             # dashes
# One-paragraph comment: what this demo does, which models it serves, and how it
# differs from its sibling variant.
spec:
  source: Custom  # community, unsupported demo blueprint (CRD enum has no "Community")
  displayName: My Demo (Ollama, CPU)
  version: 1.0.0
  description: |
    What the demo does and which component does what.

    What this CR deploys versus what runs locally, plus a pointer to the sibling
    variant.

    Prerequisites: the SUSE AI Factory operator, the application-collection
    ClusterRepo (+ credentials secret), a default StorageClass. After importing,
    create an AIWorkload from this Blueprint in the AI Factory UI.
  components:
  # ----------------------------------------------------------------------- #
  # Ollama — local LLM, CPU. Reachable in-cluster at http://ollama:11434.
  # ----------------------------------------------------------------------- #
  - chartName: ollama
    chartRepo: application-collection
    chartVersion: 1.55.0
    values:
      fullnameOverride: ollama          # pin the service name
      image:
        pullPolicy: IfNotPresent
        registry: dp.apps.rancher.io
        repository: containers/ollama
        tag: 0.21.2-11.48
      ollama:
        gpu:
          enabled: false
          draEnabled: false
        models:
          pull:
          - qwen2.5:0.5b                # literal value — never {{MODEL}}
          run:
          - qwen2.5:0.5b
        port: 11434
      persistentVolume:
        enabled: true
        accessModes:
        - ReadWriteOnce
        size: 20Gi
      service:
        port: 11434
        type: ClusterIP
  # ----------------------------------------------------------------------- #
  # Qdrant — vector store. Reachable in-cluster at http://qdrant:6333 (REST).
  # ----------------------------------------------------------------------- #
  - chartName: qdrant
    chartRepo: suse-ai-registry
    chartVersion: 1.17.0
    values:
      fullnameOverride: qdrant
      persistence:
        accessModes: ["ReadWriteOnce"]
        size: 5Gi
      service:
        type: ClusterIP
----
